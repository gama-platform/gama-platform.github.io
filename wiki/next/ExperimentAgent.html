Experiment agent: execution and maintenance

These controls and pause-state migrations are part of the unreleased 2026 development version, not GAMA 2025-06. This guide is also published on the GAMA wiki.

experiment is the agent managing the current experiment and its simulations. Execution control belongs here, not to the model species (global). From a simulation or one of its agents:

ask experiment { do pause; }
write experiment.status;

Inside an experiment's user_command, call do pause; directly. These actions target the receiving experiment's controller, not whichever experiment happens to be frontmost. They control all simulations scheduled by that experiment; they do not independently pause a single simulation. A simulation's paused attribute is deprecated and combines the experiment controller's pause state with the simulation's user-interaction hold. Use experiment.is_paused and simulation.is_on_user_hold to distinguish the two.

Execution actions​

All new controls take no arguments and return the receiving experiment agent. That return value is not a completion acknowledgement. play is queued; step_once, step_back and reload are submitted at the end of the current experiment cycle when called during execution, and then processed asynchronously by the controller. When no experiment step is in progress, submission is immediate. Do not assume that the next GAML statement sees their completed effect.

pause normally changes the scheduler state immediately, but is queued when called from a display thread. A cycle already in progress can still finish: PAUSED does not mean that every executing agent has stopped mid-action. Display synchronization changes immediately and does not change execution status.

ActionEffectUI/server counterpart and constraints
playRequests continuous execution. Does not toggle; an already running experiment stays running.UI Play / server play. An ended server execution can refuse further play; reload or a new load may be necessary according to its lifecycle.
pauseRequests a scheduler pause. Already paused stays paused.UI Pause / server pause. Does not abort the current cycle.
step_onceRequests one experiment step and leaves the controller paused.UI Step / server step with nb_steps: 1. A running cycle finishes first; the requested step is additional. In batch mode an experiment step can run an entire exploration, not one model cycle.
step_backRequests restoration of the preceding recorded states; leaves the controller paused.UI Back / server stepBack with nb_steps: 1. Requires recording and an available recorder. Restores simulations having history; without earlier history there is nothing to restore.
reloadDisposes the old experiment agent and simulations, creates fresh ones and runs initialization again.UI Reload / server reload. Uses the current experiment definition and parameter values; does not recompile edited source or accept the server command's optional parameter payload.
synchronizeMakes execution wait for display rendering.UI Synchronize enabled. Platform-wide, shared by experiments.
desynchronizeRemoves the rendering wait; execution and rendering may advance at different rates.UI Synchronize disabled. Platform-wide; some rendered frames can be skipped.

Execution commands require an active interactive controller: the regular GUI controller or a server controller. The non-interactive command-line/headless controller runs to completion and does not implement these controls; requests raise a runtime error instead of pretending to succeed. "Headless server" and "non-interactive headless" are different execution modes.

Missing/disposed controllers, unsupported controllers and failed queue submissions raise runtime errors. A deferred submission can report its error at the experiment-cycle boundary rather than at the original call site. Acceptance into the queue does not guarantee successful later execution: normal controller runtime-error handling still applies. No argument enables blocking completion, because waiting from a simulation thread could deadlock the experiment that must finish that simulation's current step.

Recording and stepping backward​

Declare recording on the experiment:

experiment Interactive type: gui record: true {
    user_command "One step" {
        do step_once;
    }
    user_command "Previous state" {
        do step_back;
    }
}

Without a recorder, step_back raises a runtime error. Recording consumes memory. Rewinding restores simulation state, not the experiment clock or external side effects such as written files, sent network messages or database operations. Random-seed behavior follows the experiment's keep_seed setting; rewinding is not necessarily a guarantee of identical subsequent random draws.

Reload and lifetime​

reload replaces the receiving agent. Its return value refers to the old agent. Reacquire experiment and simulation after reload instead of retaining them in another experiment or external client.

Reload follows the controller's existing lifecycle. In the GUI it normally resumes an experiment that was running and honors autorun; it normally leaves a manually paused experiment paused. Server reload behavior follows its own controller and load configuration. It is not an undo operation for external effects.

Do not unconditionally call reload from init: initialization will request another reload. Likewise, calling step_once every cycle deliberately keeps requesting more steps rather than providing a stable pause.

Read-only status​

AttributeTypeMeaning
statusstring"RUNNING", "PAUSED" or "NONE" from the same query used by server simulation_status_request.
is_pausedboolExperiment scheduler pause state, equivalent to status = "PAUSED". Does not include simulation user holds; false when status is "NONE".
is_synchronizedboolThe current platform-wide rendering synchronization flag.

NONE means that no controller exists or that it is disposing. NOTREADY is a transient lifecycle notification delivered to state listeners, not a value returned by this query. RUNNING/PAUSED describe controller state; they do not encode initialization errors, server stop-condition completion, wall-clock progress or a particular simulation's local pause flag. Server completion is reported separately through its existing lifecycle messages.

These attributes cannot be assigned. Change execution through actions and rendering synchronization through synchronize/desynchronize.

On simulations, read-only is_on_user_hold reports the existing user-interaction hold flag, for example while a user panel waits for input. It is not an independent scheduler-pause control: user-interaction controls manage it. simulation.paused remains a deprecated read-only compatibility query combining the controller pause and simulation hold. Its ineffective setter has been removed: assignments now fail validation instead of silently doing nothing.

Scheduler pause versus user hold​

The two flags answer different questions. For an active experiment controller:

experiment.is_pausedsimulation.is_on_user_holdDeprecated simulation.pausedMeaning
falsefalsefalseNeither a scheduler pause nor a user hold.
truefalsetrueExperiment scheduler paused; no user hold on this simulation.
falsetruetrueThis simulation is waiting for user interaction; the controller can still report "RUNNING".
truetruetrueBoth scheduler pause and user-interaction hold apply.

is_on_user_hold initially defaults to false. It reports the receiving simulation's flag, not the experiment agent's flag or another simulation's flag. User controls set the flag while waiting and clear it when released. A user panel can wait inside a cycle: this does not change the experiment's controller status to "PAUSED". play does not dismiss such a panel, and pause does not clear the hold. Release the user control through its normal interaction, then use play if the experiment scheduler is also paused.

Neither is_paused nor is_on_user_hold is writable. In particular, do not replace the old ineffective paused <- true assignment with is_on_user_hold <- true: use ask experiment { do pause; } if the intention is to pause execution. There is no new attribute-based independent pause mechanism for an individual simulation.

write experiment.is_paused;
write simulation.is_on_user_hold;

When experiment.status = "NONE", experiment.is_paused is false; this is not evidence of a running experiment. Check status when controller availability matters. A retained disposed simulation reference is not a supported way to inspect the newly reloaded simulation.

ask experiment {
    if is_paused {
        do play;
    } else if status = "RUNNING" {
        do pause;
    }
}

Use this toggle from a user command or display event. A paused experiment no longer schedules model reflexes, so a reflex cannot later resume itself. See the library recipe User Pause and Resume for a clickable example.

Synchronization is about rendering, not synchronization between agents, simulations, wall-clock time or remote clients. Without displays there is no rendering to wait for. Output configuration, synchronized-display preferences and initialization can also set this shared flag.

Existing maintenance and lifecycle actions​

ActionArgumentsEffect and return value
update_outputsRequired recompute: boolfalse refreshes the presentation of active experiment/simulation outputs without recomputing their values. true runs an output-manager step: refreshable outputs recompute and refresh according to their refresh conditions, and autosave is evaluated. Does not advance simulation agents or clocks. Returns the experiment.
update_parametersNoneRefreshes the GUI Parameters view from current values. Does not change values, reload or step simulations. This view is a frontmost-experiment GUI facility, not a separate view for background/server experiments. Without the view there is no visible effect. Returns the experiment.
compact_memoryNoneRequests JVM garbage collection across GAMA. The JVM may defer or ignore it. Does not delete reachable agents, outputs or recorded history; can cause a platform-wide pause. Returns the experiment.
dieNoneCloses this experiment, disposing its simulations, outputs and controller. Returns nil. Does not quit GAMA. No redundant exit action is provided.
ask experiment {
    do update_outputs recompute: false;
    do update_parameters;
}

Use recompute: true only when evaluation is intended: output expressions can have side effects and output-manager stepping can trigger autosave. Calling compact_memory every cycle is not a substitute for managing retained data.

ask experiment { do die; } // Close only this experiment.

The platform shutdown action is different: ask gama { do die; } quits GAMA.

Experiments also inherit ordinary agent actions: debug(message, separator, end) writes diagnostics; tell(msg, add_name) requests an information dialog; error(message) requests an error dialog. Optional debug separators/endings default to newlines; tell includes the agent name unless add_name: false. These use the configured GUI/server handlers and are not execution controls. Their return values are their message strings. The inherited _init_ and _step_ are lifecycle primitives: calling _step_ manually is not equivalent to a controller-managed step_once. Overriding them replaces the normal initialization/stepping behavior; see the library recipe Experiment and simulation.

Existing experiment attributes​

Execution control complements, rather than replaces, these existing attributes:

AttributePurpose
simulations, simulationAll current simulations and the most recently created/current simulation; the latter is nil before one exists.
parametersCurrent experiment parameter values. Updating parameter values and refreshing their GUI presentation are separate operations.
cycleThe experiment's own cycle counter. Do not confuse it with simulation.cycle, especially with multiple simulations or batch runs.
seed, rng, usageExperiment random-generator state, separate from each simulation's generator. Setting seed reinitializes the generator; zero requests a random seed.
minimum_cycle_durationMinimum wall-clock duration of a cycle in seconds, default 0. Can slow execution but does not alter simulated time.
maximum_cycle_durationUpper range of the GUI speed control in seconds, default 1; not a timeout that aborts long-running cycles.
is_guiWhether the experiment is GUI-based; not a controller-capability or running-status query.
model_path, project_pathRead-only absolute containing-folder paths, ending in a path separator.

Migration from simulation pause/resume and paused​

The model-species actions pause and resume remain available for compatibility but are deprecated in GAML documentation/validation and Java. They delegate to the owning experiment's new controls, preserving their legacy nil return. They never offered independent control of one simulation.

DeprecatedReplacement
do pause; in global, or ask simulation { do pause; }ask experiment { do pause; }
do resume; in global, or ask simulation { do resume; }ask experiment { do play; }
Reading paused for scheduler stateexperiment.is_paused
Reading paused for a user-interaction holdis_on_user_hold on the simulation
Assigning paused <- true (formerly ineffective)ask experiment { do pause; } to pause the experiment
Assigning paused <- false (formerly ineffective)ask experiment { do play; } to resume the experiment

To preserve the combined meaning of the old query, use experiment.is_paused or simulation.is_on_user_hold while the experiment has an active controller. Neither replacement attribute is assignable.

Existing model-species sleep(duration) is not a scheduler pause: it blocks the calling execution thread for a machine-time duration (seconds by default; explicit units such as 10#ms are accepted). It does not replace these experiment controls.
