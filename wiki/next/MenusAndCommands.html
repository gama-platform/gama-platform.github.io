Controls of experiments

The simulation perspective adds on the user interface a number of new menus and commands (i.e. buttons) that are specific to experiment-related tasks.

Experiment Menu​

A menu, called "Experiment", allows controlling the current experiment. It shares some of its commands with the general toolbar (see below).

The accelerators are written below with Ctrl, the spelling of Windows and Linux; on macOS the menu displays the command glyph in their place - ⌘P, ⇧⌘P, ⌘R, ⇧⌘X - and GAMA's own dialogs follow the same convention.

  • Run Experiment (Ctrl+P): runs the experiment, or pauses it when it is already running.
  • Step Experiment (Ctrl+Shift+P): runs the experiment for one cycle and pauses it after.
  • Reload Experiment (Ctrl+R): stops the current experiment, deletes its contents and reloads it, taking into account the parameters values that might have been changed by the user.
  • Stop at First Error: if checked, the current experiment stops running when an error is issued. The default value can be configured in the preferences.
  • Treat Warnings Like Errors: if checked, a warning is considered as an error (and, if the previous item is checked, stops the experiment). The default value can be configured in the preferences.
  • Display Errors and Warnings: if checked, displays the errors and warnings issued by the experiment. The default value can be configured in the preferences.
  • Simulations...: a submenu listing the simulations currently managed by the experiment, providing access to the same controls for each of them (see the agents menu).
  • Close Experiment (Ctrl+Shift+X): forces the experiment to stop, whatever it is currently doing, purges the memory from it, and switches to the modeling perspective. Use this command with caution, as it can have undesirable effects depending on the state of the experiment (for example, if it is reading files, or outputting data, etc.).

The release defines one further command in this menu, Step Back Experiment (the toolbar carries its icon and a companion command named "Previous Step"), for returning an experiment from a step to the one before it. It is not among the entries the menu offers in the simulation perspective, whether the experiment is loaded, running, or paused after a step, so this page does not describe what it does. It appears to belong to the step-by-step work described in the experiments interface page and may depend on the experiment being in that mode.

Agents Menu​

A second menu is added in the simulation perspective: "Agents". This menu allows for easy access to the different agents that populate an experiment. Its first entries are Actions and Inspect experiment, followed by Browse simulations... and one entry per running simulation (Simulation 0, Simulation 1, ...), each of them opening the menu of that simulation.

This hierarchical menu is always organized in the same way, whatever the experiment being run. A first level is dedicated to the current top-level experiment agent: it allows the modeler to inspect the agent itself and to browse its population(s) (i.e. the simulation agents). A second level lists the "micro-populations" present in each simulation agent and allows to inspect the agent itself. And the third level will give access to an overview of all the agents of the population in a table ("Browse ant population...") and to each individual agent in these populations. This organization is, of course, recursive: if these agents are themselves, hosts of micro-populations, they will be displayed in their individual menu.

Each agent, when selected, will reveal a similar individual menu. It contains a set of predefined actions (under Actions), the commands defined by the user for this species, each of them preceded by the word "Apply" (for instance "Apply Create an agent"), and then the micro-populations hosted by this agent, if any, under the form "Population of <species>". Agents (like the instances of "ant" below) that do not host other agents and whose species has no user commands will have a "simple" individual menu.

These are the actions that will be there most of the time, next to the Actions submenu:

  • Inspect: open an inspector on this agent.
  • Focus on all displays: this option is not accessible if no displays are defined. Makes all the displays zoom on the selected agent (if it is displayed) so that it occupies the whole view.
  • Highlight on all displays: makes this agent the current "highlighted" agent, forcing it to appear highlighted in all the displays that might have been defined.
  • Focus on this display: the same zoom as above, restricted to the display the menu was opened from, which is useful when several displays show the species at different scales.
  • Kill: destroys the selected agent and disposes of it. Use this command with caution, as it can have undesirable effects if the agent is currently executing its behavior.

If an agent hosts other agents (it is the case in multi-level architecture), you can access to the micro-population quite easily. The same individual menu appears when the agent is reached by right-clicking on it in a display, and it then ends with a Micro-populations section listing one entry per species the agent hosts. General Toolbar​

The last piece of user interface specific to the Simulation Perspective is a toolbar, which contains controls and information displays related to the current experiment.

This toolbar is voluntarily minimalist. Four of its buttons repeat commands of the experiment menu - Run (which becomes Pause while the experiment runs), Step, Reload and Close - and are not detailed here. Two are found nowhere else: the slider that paces the cycles, and the Synchronize button, which sits between that slider and Reload and whose tooltip reads Synchronizes the experiment with its outputs. At each end of the toolbar sit two displays: the information bar, which counts the cycles, and the status field, which reports what the workbench is doing.

The buttons carry their own explanation as tooltips, and the accelerators they state agree with the menu: Runs or pauses the current experiment (⌘P), Runs the experiment one step at a time (⇧⌘P) - greyed out while the experiment is running, since stepping and running are exclusive -, Reloads the current experiment (⌘R) and Closes the current experiment (⇧⌘X). Closing an experiment does return the workbench to the modelling perspective, as the menu announces.

The status field​

While an experiment is being opened, the status field at the right of the toolbar says what the workbench is busy with, and the words it uses are worth knowing because they are the ones a user quotes when reporting a slow start: Initializing simulations, Instantiating agents, Building outputs, then one line per display, Opening TimeSeries (finished), Opening PhasePortrait (finished). Its icon is a clock when nothing is happening and a green pair of arrows while it is working. The arrow at the right of the field opens it as a journal of all these messages, each with the time at which it was posted: the batch page shows that journal and the messages a batch adds to it.

The information bar​

The bar at the left of the toolbar is the counter of the experiment. It names the agent whose cycles it counts and gives that agent's own clock: Simulation 0: 96 cycles elapsed [00:01:36]. While a simulation is being stepped the bar is filled with a dark teal; when nothing is stepping it turns black and names the experiment instead (Experiment: 0 cycle elapsed).

The arrow at the right of the bar opens a small panel listing one row per agent that has a clock: the experiment itself and each of its simulations. Each row gives, on two lines, the number of cycles elapsed, the simulated time between brackets for the simulation agents only, and the time the machine spends on those cycles - Durations: cycle 67ms; average 26ms; total 8873 - the time a cycle takes, the average over the cycles elapsed, and the total so far. Each simulation carries the coloured disc it is drawn with on the displays. The row under the cursor is the agent the bar and the buttons act on, and the panel carries a row of buttons for that simulation. An experiment agent therefore reports its own clock, which is not the same as the clock of the simulations it has launched.

With an experiment that runs several simulations at once, the panel gives each of them a row of its own, so the four simulations alive at the same moment of a batch can be compared as they advance:

The cycle-delay slider​

The slider between the step button and the synchronize button sets the minimum duration of a step. At 0, its default at the right-hand end, steps follow one another as fast as the machine allows. Dragging the slider left imposes a minimum duration, which can make a simulation easier to follow while it runs.

The same floor can be given to the experiment itself as an attribute, which is what the slider reads and what sets the ceiling of its travel: a simulation whose steps must never be shorter than two seconds is written that way in the model rather than left to each user's mouse.
