Headless Server

GAMA's WebSocket server can control experiments in the desktop GUI as well as headless mode. The GUI experiment opens with its displays and parameter view; a client can choose its initial parameter values and receive simulation messages. Both modes use the same WebSocket protocol.

Headless command-line help and server options​

Run gama-headless.bat -help on Windows or ./gama-headless.sh -help on Linux/macOS to print the local command-line options. Running either launcher with no arguments prints the same help. These are process-startup options, not WebSocket requests:

OptionPurpose
-m <memory>Set the maximum memory (for example, 2048m).
-ws <path>Use the specified workspace.
-c, -v, -pEnable the XML parameter console, verbose mode, or external-framework pipeline.
-hpc <cores>Set the number of cores available for experimentation.
-steps <count>Set the number of steps to run.
-socket <port>Start an unencrypted WebSocket server.
-ssocket <port>Start a secure WebSocket server.
-jks <path> -spwd <password> -kpwd <password>Configure the secure server's keystore and passwords.
-ping_interval <ms>Set the server ping interval; -1 disables pings.
-no-delayDisable delayed WebSocket message sending.
-server-log, -no-server-logEnable or disable exchange logging for this launch. Disable takes precedence.
-server-log-directory <path>Select the exchange-log directory; this does not enable logging.

There is no WebSocket help command: a connected client cannot query a server for its launch options. The client protocol operates after startup and is documented below, including the load options, experiment commands, status subscriptions and server-log control. Plug-ins may contribute additional commands, so the command set can vary by installation.

The .gamx (playable model) and .gamp (project archive) commands are listed in the same help: -package <source> <output.gamx|output.gamp> generates an archive, -validate-package <archive> checks it, and -run-package <archive> [-experiment <name>] [-model <Project/model.gaml>] [-until-cycle <N>] [-output <dir>] runs one of its experiments, until cycle N or until it stops. Plugins carried by the archive, or given with -plugin <file.jar>, are only installed for the duration of the command.

For legacy -xml <experiment> <model.gaml> <parameters.xml> generation and -gaml <experiment> <model.gaml> <output-directory> execution, experiment names are case-sensitive. An unknown name produces an error identifying the requested experiment and model, lists the available non-batch experiments, and exits with a nonzero status. Batch experiments use -batch instead.

Start a headless server​

From the GAMA installation, start gama-headless.sh on Linux or macOS, or gama-headless.bat on Windows, with -socket and the port to listen on:

./gama-headless.sh -socket 1000
gama-headless.bat -socket 1000

Use -ssocket to start a secure WebSocket server. Run the launcher with -help to see the startup options supported by that installation. These options configure the server process; WebSocket commands are described below.

Default WebSocket commands​

The default protocol accepts the commands below. Each request is a JSON object whose type field contains the command name. Experiment-scoped requests use the exp_id returned by load in headless mode; the desktop server addresses its single current experiment. Plug-ins can add commands, so installations may expose more than this default set.

CommandPurpose
loadCompile a model and start a named experiment. Parameters, stop condition and message-forwarding options are described in The load request.
play, pause, step, back, stepBack, stop, reloadControl an experiment. See Experiment control commands for fields, defaults and failure responses.
expression, evaluateEvaluate a GAML expression in the experiment context; the two names are aliases. An expression beginning with ? returns keyword documentation. See Expression evaluation.
validateCheck a GAML expression supplied in expr; optional Boolean syntax selects syntax-only validation. See Validate.
askCall an action on the experiment agent or a referenced agent, with optional JSON args. See Calling agent actions.
describeCompile a server-side model file and return its experiment, species, variable and action metadata. See Describe.
upload, downloadWrite UTF-8 text to, or read UTF-8 text from, a path on the server machine. See Upload and download.
simulation_status_requestReturn the current experiment status; see simulation_status_request.
simulation_status_subscribe, simulation_status_unsubscribeEnable or disable forwarding of status-bar messages for the requesting connection; see simulation_status_subscribe and simulation_status_unsubscribe.
get_preferences, set_preferenceRead or change remotely exposed platform preferences; see get_preferences and set_preference.
server_logToggle exchange logging for the running server; see Enable or disable logging over WebSocket.
exitExit the GAMA server process. Use this only when shutting down that process is intended.

Response format and errors​

A command response has the form {"type":"...","content":...,"command":{...}}. The command member echoes the request fields (the internal server field, when present, is omitted). A command whose result is JSON returns that value as JSON in content; it is not wrapped in a JSON string. Most commands return CommandExecutedSuccessfully with empty content when they succeed. See each command below for exceptions.

Response typeMeaning
MalformedRequestA required field is missing or a field has an invalid representation.
UnableToExecuteRequestThe request is understood but cannot be completed in the current state, or a resource, action, model, or expression cannot be used.
RuntimeErrorA GAML initialization or execution error was raised while handling a command.
GamaServerErrorAn unexpected server-side error occurred; an unknown command name also uses this response.
SimulationErrorAn asynchronous simulation error, independent of the response to the command that started the work.

Asynchronous messages have type and content, and may include exp_id; they do not contain command. They include experiment lifecycle and output notifications such as SimulationStatus, SimulationEnded, SimulationOutput, and SimulationDebug. Install a message handler before sending requests because initialization output can precede the load response.

Experiment control commands​

In headless mode, these commands require the exp_id returned by load and can address only an experiment owned by the requesting WebSocket connection. A missing exp_id returns MalformedRequest; an unknown, closed, or inaccessible experiment returns UnableToExecuteRequest. In desktop GUI mode, exp_id is optional and commands address GAMA's single current experiment; when no live experiment is available, the command returns UnableToExecuteRequest unless noted otherwise below.

play​

{"type":"play","exp_id":"exp","sync":false}
FieldDefaultMeaning
exp_idRequired in headless mode; optional in GUI modeExperiment to start.
syncfalseIn headless mode, wait for completion only when this is true and either the request has a non-empty until field or the experiment is a batch experiment. GUI mode does not use this field to defer the reply.
untilNo effect on the stop conditionIn headless mode, a non-empty value marks this play request for deferred completion when sync is true. Set the actual stop condition on load.until or in the model.

Success returns CommandExecutedSuccessfully. Headless mode reports UnableToExecuteRequest if the controller cannot start. GUI mode reports it when no experiment is loaded, the simulation has ended, or the controller is full. In GUI mode, the reply acknowledges the start request; use the asynchronous SimulationEnded message to detect completion.

pause​

{"type":"pause","exp_id":"exp"}
FieldDefaultMeaning
exp_idRequired in headless mode; optional in GUI modeExperiment to pause.

Success returns CommandExecutedSuccessfully with empty content. If the controller cannot pause the experiment, the server returns UnableToExecuteRequest.

step​

{"type":"step","exp_id":"exp","nb_step":1,"sync":false}
FieldDefaultMeaning
exp_idRequired in headless mode; optional in GUI modeExperiment to advance.
nb_step1Number of simulation steps to request. An integer is expected.
syncfalseWait for the requested step operation before returning when true.

Success returns CommandExecutedSuccessfully with empty content. If the simulation has ended or the controller cannot accept the operation, the response is UnableToExecuteRequest. A runtime error raised during a synchronous step is returned as RuntimeError. A non-integer nb_step is rejected as a server-side command error.

back and stepBack​

The two command names are aliases:

{"type":"back","exp_id":"exp","nb_step":1,"sync":false}
FieldDefaultMeaning
exp_idRequired in headless mode; optional in GUI modeExperiment whose recorded state to restore.
nb_step1Number of recorded steps to go back. An integer is expected.
syncfalseWait for the operation before returning when true.

The experiment must declare record: true and have a previous recorded state. Success returns CommandExecutedSuccessfully with empty content; otherwise the command returns UnableToExecuteRequest. A non-integer nb_step is reported as a server-side command error.

stop​

{"type":"stop","exp_id":"exp"}
FieldDefaultMeaning
exp_idRequired in headless mode; not used in GUI modeHeadless mode closes the addressed experiment. GUI mode closes the current GAMA experiments.

Success returns CommandExecutedSuccessfully with empty content. Headless mode can return UnableToExecuteRequest when the experiment cannot be resolved and GamaServerError if closing it throws an unexpected error. Stop closes the experiment; it does not shut down the server. Discard the old headless exp_id and use load to create another experiment.

reload​

{"type":"reload","exp_id":"exp","parameters":{"var1":42},"until":"completed >= 10","seed":7}
FieldDefaultMeaning
exp_idRequired in headless mode; optional in GUI modeExperiment to initialize again.
parametersKeep current parameter valuesOptional overrides, using the same object or array forms as load.
untilNo override; an omitted or empty value clears the existing client stop-condition overrideBoolean GAML stop-condition expression.
seedNew engine-generated seedFinite numeric seed for the next run.

Success returns CommandExecutedSuccessfully with empty content; keep the same exp_id. Invalid parameter or seed values return MalformedRequest. An initialization error returns RuntimeError; a controller that cannot reload returns UnableToExecuteRequest. Message-forwarding options from the original load are retained. In headless mode, a running experiment is paused and the current cycle is allowed to finish before reinitialization; a paused experiment remains paused.

Expression and model commands​

expression and evaluate​

These names are aliases. Evaluate an expression in the current experiment context:

{"type":"expression","exp_id":"exp","expr":"agents count"}
FieldDefaultMeaning
exp_idRequired in headless mode; optional in GUI modeExperiment context in which to evaluate the expression.
exprRequiredGAML expression, trimmed before evaluation. If it begins with ?, the remainder is looked up as a GAML keyword or operator and its documentation is returned.

On success, content contains the evaluated value as JSON. Missing expr returns MalformedRequest. An expression that cannot be compiled or evaluated, or produces no result, returns UnableToExecuteRequest; its content contains the evaluation error text. The command does not modify the model source file.

validate​

Validate GAML text without loading an experiment:

{"type":"validate","expr":"int total <- 1 + 2;","syntax":false}
FieldDefaultMeaning
exprRequiredGAML text to validate. An empty or whitespace-only string succeeds.
syntaxfalseJSON boolean. false performs syntax and semantic validation; true requests syntax-only validation.

Success returns CommandExecutedSuccessfully with empty content. Missing expr returns MalformedRequest. Compilation errors return UnableToExecuteRequest; content is a JSON compilation-error report. A non-boolean syntax value is treated as false; send a JSON boolean to make the selected mode explicit.

describe​

Compile a model file on the server and return its metadata. This command does not require a loaded experiment:

{"type":"describe","model":"/path/to/model.gaml","experiments":true,"speciesNames":true,"speciesVariables":true,"speciesActions":true}
FieldDefaultMeaning
modelRequiredPath to a GAML model file on the server machine.
experimentstrueInclude experiment names and parameter metadata.
speciesNamestrueInclude species entries. This is also forced on when either species variables or actions are requested.
speciesVariablestrueInclude each species' variable names and GAML types.
speciesActionstrueInclude each species' action names, parameter names and types, and return type.

Success returns a JSON object with name and path, and the requested experiments and species arrays. Experiment entries contain name and parameters (name, description, and type). Species entries contain name, and may contain variables (name, type) and actions (name, parameters, type). Missing model returns MalformedRequest; a missing path, non-GAML file, I/O problem, or compilation failure returns UnableToExecuteRequest. Supply the flags as JSON booleans; invalid representations can produce GamaServerError.

upload and download​

These commands access the filesystem of the computer running GAMA. They transfer UTF-8 text; they are not binary-file transfer commands.

Upload text to a server-side path (an existing file is overwritten):

{"type":"upload","file":"/path/on/server/output.txt","content":"text to write"}

Download text from a server-side path:

{"type":"download","file":"/path/on/server/output.txt"}
FieldDefaultMeaning
fileRequiredServer-side filesystem path.
contentRequired for upload; unused by downloadText to write as UTF-8.

upload creates or truncates the target file but does not create missing parent directories. It returns CommandExecutedSuccessfully with empty content; missing fields return MalformedRequest, and filesystem errors return UnableToExecuteRequest with the underlying error text. download returns the file text in content; line endings are normalized to \n and a final line ending is not preserved. A missing file returns MalformedRequest; read failures return UnableToExecuteRequest.

exit​

{"type":"exit"}

This command takes no additional fields and terminates the entire GAMA server process (and the desktop application when sent to its embedded server). The implementation exits before the socket can reliably deliver its nominal success response. Expect the WebSocket connection and server process to close; send this only when shutting down that process is intended.

File transfer, model loading, expression evaluation, and preference changes act on the server machine or running GAMA instance. Make the endpoint available only to trusted clients. The protocol does not provide authentication or restrict a connected client to read-only operations.

Enable the desktop server​

The desktop WebSocket server is disabled by default. To enable it in GAMA, open Preferences > Network > Server mode, select Enable GAMA server mode, and check Port to which GAMA server is listening (default: 1000). Connect to ws://localhost:1000, substituting your configured port.

To set the desktop-server preference in GAMA's launcher configuration, edit the Gama.ini file. Add the JVM property after the existing -vmargs line; if the file has no -vmargs line, add one before the property:

-vmargs
-Dpref_enable_server=true

The JVM property overrides the saved preference for that launch. Use -Dpref_enable_server=false to force it off. To change the saved setting instead, use the Preferences view and restart GAMA. This preference controls the desktop server; the command-line headless launcher starts a WebSocket server when given -socket <port> or -ssocket <port>.

The GUI server has one current experiment, shared with the desktop user; it does not create an independent simulation for every connection. Loading another experiment replaces the current one, subject to GAMA's normal close-confirmation dialog. Connecting another client does not transfer the loaded experiment's output to that client.

Use this server on a trusted network. Clients can load local models and execute GAML; the desktop WebSocket endpoint is not an authenticated public service.

Desktop server console and controls​

Open Views > Show View... > Server Console in either the modeling or simulation perspective. This view is independent of the experiment consoles and remains available when the model layout hides them. It shows the server state, listening port, connected client identifiers and addresses, incoming requests, and errors with stack traces. Diagnostics are retained while the view is closed and across GUI server restarts, within a bounded journal (2,000 events / 200,000 characters, with individual messages capped at 16,384 characters). Search, pause, clear, text sizing, and log export use the same controls as the execution console. Server controls are grouped on the left of the toolbar; console controls are on the right. The magnifier (or Cmd/Ctrl-F) opens the native Find overlay with the same custom icons as the GAML editor. Find supports the execution, interactive, and server consoles, without allowing replacement of console text. Clearing the view clears its displayed text, not the retained server journal.

The toolbar provides Start, Stop, and Restart without changing the saved startup setting. The separate pause button pauses console output only, not the server or experiment. Stopping or restarting disconnects clients but does not close the desktop experiment. The Port selector beside Restart stages a new port without interrupting the server. Click Start or Restart to save and use it; startup/binding failures appear in the console. Clients (N)... is also in the toolbar, lists connected clients, and is disabled when none are connected. The server starts disabled by default. Enable at startup changes the saved preference as well as the current server state.

The Server options section at the end of the three-dots menu can hide incoming requests, enable persistent exchange logging, and open the current run's exchange log. Its Enable at startup option saves the existing server-mode preference and also starts or stops the current server. Requests are still retained while hidden. Export the visible console text for a diagnostic/error log; enable exchange logging for a complete protocol journal. These are local GUI controls, not new remote administration commands or an additional network endpoint.

Platform preference commands​

GUI and headless servers accept these commands without loading an experiment. They operate on GAML-accessible preferences registered in the running installation, including plug-in preferences. Internal preferences that are not exposed in GAML cannot be read or changed through these commands.

get_preferences​

Read selected preferences, or omit names to discover all remotely exposed preferences:

{"type":"get_preferences","names":["pref_experiment_ask_closing"]}

The CommandExecutedSuccessfully response's content is an object keyed by preference name. Each entry contains value, type, description, restart_required, min, max, and among. Unspecified constraints are null. An empty names array selects nothing; unknown or unexposed names cause the entire read to fail.

set_preference​

To suppress the GUI's experiment-replacement confirmation, send this command and wait for its successful response before sending load:

{"type":"set_preference","name":"pref_experiment_ask_closing","value":false}

Changes are runtime-only by default. Add "persist":true to save the value for subsequent launches. The response's content contains the same metadata as a read, plus name and persisted (whether persistence was requested and completed). restart_required means the new value is stored but may not take effect until GAMA restarts; the command never restarts GAMA automatically. Setting the current value is harmless and can still explicitly persist it.

Values use the following JSON representations, both when reading and writing:

Preference typeJSON value
boolBoolean, not "true" / "false" strings.
intIntegral number in the signed 32-bit range.
floatFinite number.
stringString, including for enumerated string preferences.
rgb (color)[red, green, blue, alpha], integer components in 0..255; writes also accept three components (alpha defaults to 255).
font{"name":"Helvetica","style":0,"size":12}; style 0..3 (plain, bold, italic, bold italic), positive integer size.
point[x,y,z]; writes also accept [x,y] with z=0.
dateISO date/time string.
fileNon-empty server-side path string.

Missing fields, null values, incorrect types, unsupported write types, unknown keys, and values outside declared ranges or allowed choices return MalformedRequest. Listener vetoes or update/persistence failures return UnableToExecuteRequest. Persistence or listener failures can occur after an in-memory change; read the preference again to determine its effective value. Changes use normal preference listeners, on the GUI thread when applicable.

Preferences are global to the running GAMA instance, not to an experiment or connection. They affect the desktop user and other clients and are not restored on disconnect. Only trusted clients should access the server: GAML visibility is not an authorization mechanism, and any connected client can modify exposed preferences. There are no batch writes or preference-change subscriptions.

Server exchange logs​

Exchange logging is off by default, in both GUI and headless modes, including secure (wss://) headless servers. When enabled, each server run creates a separate UTF-8 JSON Lines file in ~/.gama/server-logs/, outside the temporary headless workspace. The startup console prints its absolute path, for example:

GAMA server exchange log: /home/alice/.gama/server-logs/server-1000-123456789.jsonl

The log records every received and sent WebSocket frame, including malformed JSON requests, command replies, asynchronous simulation output/errors, broadcasts (one record per recipient), binary data, fragmented messages, and ping/pong/close frames. Logging happens below command processing, so messages rejected or consumed by listeners are also captured. It does not enable simulation output that a client has chosen not to receive.

Enable logging or change its directory​

In desktop preferences, open Network > Server mode:

PreferenceDefault
Log all GAMA server exchangesDisabled
Server exchange log directory (restart required)~/.gama/server-logs

Changing the logging preference takes effect immediately on a running GUI server, without restarting GAMA or disconnecting clients, and is saved for future launches. If enabling fails, an error is shown and the preference change is rejected. The directory preference still requires restarting the server; toggling logging off and on keeps the same run's file.

In headless mode, use launch-only options instead:

./gama-headless.sh -socket 1000 -server-log
./gama-headless.sh -socket 1000 -server-log -server-log-directory "/path/to/server logs"
./gama-headless.sh -socket 1000 -no-server-log

On Windows, use the same options with gama-headless.bat. These options also work with -ssocket secure servers and do not modify saved preferences.

Headless optionEffect for this launch
-server-logEnable exchange logging.
-no-server-logDisable exchange logging, even if -server-log is also present.
-server-log-directory <path>Override the output directory; does not itself enable logging. Quote paths containing spaces.

Launch options take precedence over JVM properties, which take precedence over saved preferences. With no launch overrides, the existing settings are retained. For either mode, the optional JVM properties remain available: -Dgama.server.log=true, -Dgama.server.log=false, and -Dgama.server.log.directory=/absolute/path/to/logs.

These precedence rules determine startup behavior. A subsequent GUI preference change or remote command overrides the running state immediately.

Enable or disable logging over WebSocket​

In GUI or headless mode, send a server_log command to toggle logging immediately, without restarting or loading an experiment:

{"type":"server_log","enabled":true}

To disable it:

{"type":"server_log","enabled":false}

enabled is required and must be a JSON boolean, not a string. A successful response has type CommandExecutedSuccessfully and content containing enabled and log_file (the absolute server-side path, or null if no log file has been created). Invalid requests return MalformedRequest; file creation/write failures return UnableToExecuteRequest.

This changes logging for the whole running server, including all connected clients, not only the requesting connection. Any connected client can toggle it; use this only with trusted clients. It overrides the current launch setting but does not change JVM properties or saved preferences. The next server launch uses its normal configuration again. The output directory remains the one configured locally; this command cannot select an arbitrary remote file path.

Enabling starts recording subsequent traffic, including the enable response; earlier exchanges cannot be recovered. Disabling records the request and a logging_disabled boundary, then closes the file before replying, so the disable response is not recorded. Re-enabling appends to the same run's file with a logging_enabled boundary and continuing sequence numbers. Repeating the current setting is harmless. A connection opened while logging was off has no earlier connection_opened record, but its subsequent frames still include its socket ID and remote address.

Log format and troubleshooting​

Each line is a JSON object with a UTC timestamp, an increasing per-run sequence, and an event. The server_started record includes the listening port and GAMA version; connection-open/close records identify the socket and remote address. Frame records also include:

FieldMeaning
socket_id, remote_addressConnection identity, allowing concurrent clients to be distinguished.
directionreceived (client to server) or sent (server to client).
opcode, finWebSocket frame type and whether it is the final fragment.
encoding, payloadComplete, untruncated payload: utf-8 text for complete text frames, or lossless base64 for binary, control, and fragmented frames.

For example, a frame may be recorded as:

{"timestamp":"2026-10-24T04:42:00Z","sequence":3,"event":"frame","socket_id":"12345","remote_address":"/127.0.0.1:54321","direction":"received","opcode":"TEXT","fin":true,"encoding":"utf-8","payload":"{\"type\":\"play\",\"exp_id\":\"exp\"}"}

Text is JSON-escaped, so even payloads containing newlines occupy one log line. For a fragmented message, concatenate the decoded payloads from its initial TEXT/BINARY frame and subsequent CONTINUOUS frames on the same socket until fin is true; control frames can occur between fragments. HTTP upgrade handshakes and TLS traffic are not logged. sent means submitted for WebSocket serialization, not proof that the client received it.

Records are serialized across threads and flushed after every write, allowing inspection while the server is running. This adds disk I/O to message handling. Shutdown while logging is enabled closes the file with a server_stopped record; that record is absent if logging was disabled or the process crashed. If the configuration is invalid, the directory cannot be created, or a write fails (for example, disk full), an explicit GAMA server exchange logging unavailable error is printed to stderr. The server continues handling clients, but recording stops. After fixing the cause, a server_log enable command can retry.

Treat these files as sensitive: they contain complete messages without redaction, including model paths, parameter values, executed expressions, outputs, and any credentials or personal data present in payloads. TLS does not protect the local log. Review/redact a copy before attaching it to a bug report. Files are not rotated or automatically deleted: monitor disk usage, archive/remove old runs yourself, or disable logging when it is not appropriate. When reporting a server problem, include the relevant run's log together with the model and reproduction steps.

Calling agent actions with ask​

The agent field is an agent reference, not a GAML expression. For example:

{"type":"ask","exp_id":"exp","agent":"simulation[0].boids[12]","action":"say_hello","args":{"the_value":12}}

Use the reference returned when an agent is serialized by the server. References start at the simulation and can include nested populations. one_of(boids) is not a reference; evaluate it with an expression request first to obtain an agent reference, then use that reference in ask. Omit agent to call an action on the experiment agent.

action must be a non-empty string. args accepts a JSON object or, for compatibility with existing clients, a string containing a JSON object (for example, "args":"{\"the_value\":12}"). Omitting args supplies no arguments. Malformed references or arguments return MalformedRequest; missing/dead agents and unknown actions return UnableToExecuteRequest. Resolving an ask target does not create missing agents.

The load request​

{
  "type": "load",
  "model": "/absolute/path/to/server_load.gaml",
  "experiment": "exp",
  "parameters": { "var1": 42 },
  "until": "completed >= 10",
  "console": true,
  "status": false,
  "dialog": false,
  "runtime": true
}
FieldDefaultMeaning
modelRequiredPath to a .gaml file on the machine running GAMA, not on the client. Absolute paths are recommended.
experimentRequiredName of an experiment declared in the model.
parametersNo overridesEither an object mapping parameter names to values (for example, { "var1": 42 }) or the legacy array of { "name": "...", "value": ... } objects. Names can be parameter titles (such as "param") or variable names (such as "var1"). In the array form, type is optional; "int" and "float" also accept numeric strings.
seed0 (request a new engine-generated seed)Finite numeric seed for the experiment. Supply a number to make the initialization use that seed.
untilNo client overrideBoolean GAML expression evaluated in the simulation scope. If omitted, the model's experiment stop condition is retained.
consoletrueForward console output (SimulationOutput and SimulationDebug). The global Send console outputs to clients preference must also be enabled.
statusfalseForward status-bar messages (SimulationStatusInform, SimulationStatusError, SimulationStatusNeutral); see Status message flow.
dialogfalseForward information/error dialog messages (SimulationDialog, SimulationErrorDialog). This does not remotely answer interactive questions.
runtimetrueForward asynchronous runtime errors (SimulationError). Command failures are still returned when this is false.

Parameter values are applied before the simulation's global init executes, so initialization and the parameter view use the supplied values immediately. Parameters omitted from the request keep their model defaults.

Model paths can contain spaces in both file and directory names, including on macOS. Send the plain filesystem path (for example, "/Users/alice/My models/Model with spaces.gaml"), not a URL-encoded or shell-escaped path. In the HTML connector's path field, omit the JSON quotes and click the checkmark to apply the model and experiment.

Missing model or experiment, malformed parameter entries, or a non-finite seed return MalformedRequest. Missing model files, a file that is not GAML, an unknown experiment name, or a compilation failure return UnableToExecuteRequest; an error while initializing the experiment can return RuntimeError. The error content may contain a compilation report as JSON.

Forwarding settings are associated with the experiment and its requesting connection, including during initialization and reload. In GUI mode they only control the extra WebSocket messages: they do not hide the local console, status bar, dialogs or errors. Local modal dialogs may still require a desktop user's response.

Both GUI and headless servers also send lifecycle notifications of type SimulationStatus (for example RUNNING or PAUSED). These are control notifications, independent of the status option.

simulation_status_subscribe​

The status load option sets the initial forwarding preference for status-bar messages. The owning client can change it while the experiment is loaded:

{"type":"simulation_status_subscribe","exp_id":"exp"}

This enables forwarding of SimulationStatusInform, SimulationStatusError and SimulationStatusNeutral messages without reloading the experiment. While a simulation is running, the change is processed at an experiment step boundary. It does not affect local GUI status output or the GUI's lifecycle SimulationStatus notifications. A successful command returns CommandExecutedSuccessfully with content set to {"status":true}. In headless mode, include the exp_id returned by load; GUI mode can resolve its single current experiment without an exp_id. Only the connection that loaded the experiment can change its status subscription.

The only request field is exp_id (required in headless mode and optional in GUI mode). Missing or inaccessible experiments return MalformedRequest or UnableToExecuteRequest, respectively. A connection other than the one that loaded a headless experiment cannot change that experiment's subscription.

simulation_status_unsubscribe​

Send this request to stop forwarding status-bar messages for the experiment:

{"type":"simulation_status_unsubscribe","exp_id":"exp"}

The change takes effect without reloading and is processed at an experiment step boundary while a simulation is running. A successful command returns CommandExecutedSuccessfully with content set to {"status":false}. This affects WebSocket forwarding only; local GUI status output and lifecycle SimulationStatus notifications continue. Only the connection that loaded the experiment can change its subscription.

The only request field is exp_id (required in headless mode and optional in GUI mode). Missing or inaccessible experiments return MalformedRequest or UnableToExecuteRequest, respectively. A connection other than the one that loaded a headless experiment cannot change that experiment's subscription.

simulation_status_request​

Request a snapshot of the current lifecycle state:

{"type":"simulation_status_request","exp_id":"exp"}

The server replies with a SimulationStatus message, for example {"type":"SimulationStatus","content":"PAUSED","exp_id":"exp"}. This snapshot is independent of the status-bar subscription, so a client can unsubscribe from status-bar messages and still request the current state. A headless request needs exp_id; it is optional in GUI mode.

The only request field is exp_id (required in headless mode and optional in GUI mode). Missing or inaccessible experiments return MalformedRequest or UnableToExecuteRequest, respectively.

Experiment lifecycle status (SimulationStatus)​

SimulationStatus reports the execution state of an experiment. It is a lifecycle notification, not text from the GAMA status bar. The server sends it in both GUI and headless modes when the experiment-state listener receives an update. The load process can temporarily defer these updates so the client receives the load response, including its exp_id, before the deferred lifecycle state.

The message has the experiment identifier in exp_id and the state name as a plain string in content:

{"type":"SimulationStatus","content":"RUNNING","exp_id":"exp"}

The pushed lifecycle values used by the server are NOTREADY, RUNNING, PAUSED and NONE. NOTREADY marks initialization or another controller operation that temporarily makes execution unavailable. When a controller is disposing, the server reports NONE, even if a late update would otherwise report RUNNING or PAUSED. Repeated updates with the same state for the same experiment and connection are suppressed. The FINISHED enum value is not the server's run-completion event: when a stop condition is reached, the experiment pauses and the server sends a separate SimulationEnded event.

simulation_status_request returns a snapshot using the same SimulationStatus message format. It derives that snapshot from the controller: RUNNING, PAUSED or NONE. It does not subscribe the client to future messages, and the snapshot does not include transient NOTREADY updates. A request requires the experiment's exp_id in headless mode; it is optional in GUI mode. The requesting connection must own the experiment.

During load, lifecycle updates are deferred until after the command response. If several state updates happen while loading, the server keeps the latest one for delivery. Install a WebSocket message handler before sending load so the client can store its exp_id from the response and then process the corresponding lifecycle notification. Other asynchronous message types are not necessarily deferred and can arrive before the load response.

Status-bar messages​

Status-bar messages are separate from experiment lifecycle status. GAMA or model code can publish informational, error or neutral text in the local status bar. The WebSocket forwards these messages only when the experiment's status forwarding is enabled: load.status defaults to false, and simulation_status_subscribe or simulation_status_unsubscribe changes the setting for the owning connection. console is an independent option that controls SimulationOutput and SimulationDebug messages.

An example status-bar update wraps its JSON-text payload as a string in the outer message; clients that need the individual message, icon or color values can parse content a second time:

{"type":"SimulationStatusInform","content":"{\"message\":\"Loading data\",\"icon\":null}","exp_id":"exp"}

Status errors use SimulationStatusError with a message field in that inner JSON text. Disabling status-bar forwarding affects only WebSocket delivery; it does not change local GAMA status output. The lifecycle SimulationStatus messages and the SimulationEnded completion event are not disabled by this setting.

To enable status-bar messages for an already loaded experiment, send simulation_status_subscribe and wait for its successful response. While the experiment is running, the change is applied between simulation cycles. The acknowledgement reports the new subscription state; it does not replay earlier status-bar messages.

Responses and completion​

A successful GUI load returns CommandExecutedSuccessfully with the experiment name in content. Use that returned string as exp_id in subsequent requests. Headless mode returns its generated experiment ID instead. Missing required fields or malformed parameter objects return MalformedRequest; missing files, unknown experiments and invalid stop conditions return UnableToExecuteRequest.

Output from global init can arrive before the load response. Always install a message handler before sending the request, and distinguish command responses (which include command) from asynchronous simulation messages.

Send {"type":"play","exp_id":"exp"} to run the experiment. GUI experiments retain their usual autorun preference; declare autorun: false if the client should start execution explicitly.

In headless mode, play applies the start transition and sends RUNNING before acknowledging success, without waiting for a simulation cycle. The simulation still runs asynchronously. A headless play with sync: true and a non-empty until field in that play request, or a batch experiment, retains its deferred response until completion. The play.until field only controls response timing; the stop condition itself must be declared by the model or supplied as load.until.

The stepBack command (or its back alias) requires an experiment declared with record: true. In both GUI and headless modes, non-record experiments return UnableToExecuteRequest with an explanation, whether sync is omitted, false, or true; no backward step is submitted to the controller.

When the stop condition becomes true, the GUI experiment pauses and emits one SimulationEnded event with empty content and its exp_id. No further steps are executed until the experiment is reloaded. The displays remain open for inspection.

Send a reload request to initialize another run. Forwarding settings are retained. reload can supply new parameters in either supported format and until; parameters omitted from reload retain their current values. An omitted or empty reload until clears the previous stop condition, so resend it to retain a limit.

In headless mode, reloading a running experiment pauses execution and waits for the current experiment cycle to finish before rebuilding it, then resumes execution. An experiment that was paused stays paused.

stop closes the experiment, unlike pause or reaching an until condition. Wait for its CommandExecutedSuccessfully response before sending another lifecycle command, discard the old exp_id, and use load (not reload) to open an experiment again. The GUI sends SimulationStatus with content NONE when closing; a finishing cycle cannot change a disposing experiment back to PAUSED or RUNNING. Lifecycle notifications and command replies are separate messages and can arrive in either order. Successful reload replies have empty content: keep the existing exp_id rather than replacing it.

GUI mode remains interactive, single-experiment mode, not a replacement for headless multi-experiment execution. In particular, GUI play acknowledges starting execution; it does not implement headless play's deferred sync: true response. Wait for SimulationEnded to detect completion.

Compatibility notes: Stop lifecycle correction (#988)​

This correction does not change GAML syntax, WebSocket command names, JSON fields, or response formats. Existing models do not require changes, and headless command handling is unchanged. The following observable behavior changes apply:

SurfaceChange
Experiment state queriesGAMA.getExperimentState() returns NONE for a disposing controller, even if its paused flag is still set.
GUI lifecycle notificationsA disposing experiment cannot emit a late PAUSED, RUNNING, or NOTREADY state after closure. Notifications are serialized to preserve delivery order.
GUI notification deduplicationA different experiment or destination connection can receive a notification even when the state name is unchanged. Clients must not assume a fixed notification count.
Bundled browser connectorLoad, Reload and Stop requests wait for their replies before another Load, Reload or Stop can be sent, including with Headless mode enabled. This is a connector-side restriction, not a new server protocol requirement.

Clients should process lifecycle notifications as state updates, not count them or depend on transient shutdown states. Treat a successful Stop reply as confirmation that the experiment is closed; use Pause to suspend an experiment that should later resume. Keep command-response handling separate from asynchronous status handling. Clients following these rules should remain compatible; clients relying on the previous shutdown race or notification suppression may need adjustments.

Headless batch experiments​

For a mode: batch experiment, play runs the complete exploration, including all parameter sets and repetitions. The experiment's until condition (or its override supplied by load) stops each individual simulation, not the whole batch. The server emits one SimulationEnded event when the exploration finishes, even without a client-supplied until. A batch play with sync: true defers its response until that event. Further play and step requests are refused once the batch is complete; load a new experiment to run another batch.

Complete example​

Save this model as server_load.gaml on the GAMA machine:

model server_load

global {
    int var1 <- -100;
    int completed <- 0;

    init {
        write "Initial value: " + var1;
    }

    reflex tick {
        completed <- completed + 1;
    }
}

experiment exp mode: gui autorun: false {
    parameter "param" var: var1;
}

Save the following client as client.mjs. It uses the built-in WebSocket client in Node.js 22 or later, so no packages are needed:

const model = process.argv[2];
if (!model) throw new Error("Usage: node client.mjs /absolute/path/to/server_load.gaml");

const socket = new WebSocket("ws://localhost:1000");
socket.addEventListener("error", event => {
  console.error("WebSocket error", event);
  process.exitCode = 1;
});
socket.addEventListener("message", event => {
  const message = JSON.parse(event.data);
  console.log(message);

  if (message.command?.type === "load") {
    if (message.type !== "CommandExecutedSuccessfully") {
      process.exitCode = 1;
      socket.close();
      return;
    }
    socket.send(JSON.stringify({ type: "play", exp_id: message.content }));
  } else if (message.type === "SimulationEnded") {
    socket.close();
  } else if (message.command && message.type !== "CommandExecutedSuccessfully") {
    process.exitCode = 1;
    socket.close();
  }
});
socket.addEventListener("open", () => {
  socket.send(JSON.stringify({
    type: "load",
    model,
    experiment: "exp",
    parameters: { var1: 42 },
    until: "completed >= 10",
    console: true,
    status: false,
    dialog: false,
    runtime: true
  }));
});

Run it while the desktop GAMA server is enabled:

node client.mjs /absolute/path/to/server_load.gaml

The local GAMA console and the client's SimulationOutput message should show Initial value: 42, not -100. The parameter view should show 42. After ten executions of tick, the client receives SimulationEnded and the GUI remains paused with completed = 10.
